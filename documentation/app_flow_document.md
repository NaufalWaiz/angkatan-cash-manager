# App Flow Document

## Onboarding and Sign-In/Sign-Up

A new visitor arrives at the application by navigating to the public landing page in their browser. This page welcomes users with a brief introduction to the class treasury management app and invites them to either sign up for a new account or sign in if they already have one. When the user clicks “Sign Up,” they are taken to the Clerk-powered registration page, where they can enter their email address and choose a secure password. Clerk may also offer social login options such as Google or GitHub; users simply select the option they prefer and follow the provider’s prompts to grant access. After completing registration, Clerk sends a confirmation link or magic link via email. Clicking that link verifies the account and automatically logs the user in. If the user already has an account, clicking “Sign In” brings up Clerk’s login form, where they enter their credentials or use one of the configured social login buttons. At any point, if a user forgets their password, they click “Forgot Password” on the login form, enter their email, and receive a password reset link. Once they follow that link, they set a new password and return to the sign-in screen. A visible “Log Out” button appears in the header once the user is authenticated, allowing them to securely end their session and return to the landing page.

## Main Dashboard or Home Page

After a successful sign-in, the user is redirected to the dashboard at `/dashboard`. The dashboard displays a consistent header across all views with the app logo on the left and a user avatar or name on the right, which opens an account menu. Below the header, a sidebar runs down the left side, offering links to the main areas: Dashboard, Submit Payment, Expenses, and Account Settings. The remainder of the screen is the main content area. For Students, this area shows summary cards highlighting the total funds collected so far and the total class expenses. Interactive charts and cards provide a quick visual overview of the class treasury status. For Treasurers, the same dashboard view includes an approval queue table listing student payment submissions that are pending review. Each row in the table has buttons labeled “Approve” and “Reject,” enabling the Treasurer to take action directly from the dashboard.

## Detailed Feature Flows and Page Transitions

When a Student wants to submit a payment, they click the “Submit Payment” link in the sidebar and land on a new page with a form built using `shadcn/ui` components. The form prompts for fields such as payment amount, date, and an upload component for proof of payment. After filling in all fields and attaching a document image or PDF, the student clicks “Submit.” The form data is sent as a POST request to `/api/payments`, where the backend uses Drizzle ORM to insert a new record in the Supabase database with status set to pending. Once the submission succeeds, the user sees a confirmation message and a button to return to the dashboard or submit another payment. When a Treasurer accesses the same “Submit Payment” page, they are redirected back to the dashboard because they cannot submit payments as a student. Instead, they stay on the dashboard, where the pending payments table is updated in real time when new submissions arrive. To approve a payment, the Treasurer clicks the “Approve” button beside a row. That action triggers a PATCH request to `/api/payments/:id` with a payload marking the item as approved. The table row then disappears or changes color to indicate the new status. If the Treasurer rejects a submission, a small modal appears inviting them to optionally enter a rejection reason, then sends a PATCH request updating the status to rejected. All users can visit the “Expenses” page via the sidebar, where a data table fetches records from `/api/expenses` and lists every class expense that has been recorded. This page is paginated and searchable and allows both roles to view the expense history in detail.

## Settings and Account Management

Users manage their profile by clicking the avatar menu in the header and selecting “Account Settings.” This takes them to a page where they can update personal details such as display name, profile picture, and contact email. If they signed up via social login, they see which provider is connected and have the option to add or remove other providers. Notification preferences appear on the same page, letting users toggle email alerts for new approvals, rejections, or other system messages. Treasurers have an additional section in Settings where they can view a list of users and assign the "Treasurer" role to additional accounts through a simple interface that updates user roles in the database. After making changes, users click “Save Changes” and a confirmation banner appears at the top. A “Back to Dashboard” link in the page header returns them to the main flow.

## Error States and Alternate Paths

If a user attempts to sign in with incorrect credentials, Clerk displays an inline error message under the login form fields. In the case of a network failure during sign-in or sign-up, a banner appears at the top of the page explaining connectivity issues and suggesting the user check their internet connection. During payment submission, if a required field is missing or the uploaded file format is not supported, the form highlights the offending input with a red border and an error message explaining how to correct it. Should the POST request to `/api/payments` fail on the server side—due to a database error or permission check—the user sees a modal informing them that their submission could not be processed and inviting them to try again later. If a Student tries to navigate directly to the Treasurer’s approval actions by entering an admin URL, the system returns a 403 Forbidden page with a message explaining they lack the required permissions and provides a link back to the dashboard. All unexpected server errors lead to a generic error page advising users to refresh or contact support if the issue persists.

## Conclusion and Overall App Journey

In summary, a brand-new user begins on the public landing page before signing up through Clerk’s intuitive flow, confirms their email, and signs in for the first time. They land on a personalized dashboard that adapts to their role. Students submit payment proofs on a dedicated page and immediately return to a dashboard showing high-level financial summaries. Treasurers manage an approval queue from the same dashboard, approving or rejecting submissions with a single click. Both roles can access a transparent list of all recorded expenses and personalize their account details in the settings area. Throughout the experience, clear navigation, consistent layouts, and helpful error messages ensure a smooth, end-to-end journey from account creation to everyday use of the class treasury management application.
